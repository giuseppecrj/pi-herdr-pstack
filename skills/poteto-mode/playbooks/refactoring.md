### Refactoring

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work belongs to the **figure-it-out** skill (planned W4). Until it ships, follow the hub's fallback for large efforts. This playbook is the focused-to-medium change.

1. Pin the behavior contract first. Run the **how** skill (planned W4) over the affected subsystem to learn the contract, or investigate it directly per `playbooks/investigation.md` until it ships. Then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
2. Name the structure the code is missing per **principle-model-the-domain** (planned W3). Boring code stays when the shape is already clear and local. The reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (**principle-foundational-thinking**, **principle-redesign-from-first-principles**, both planned W3). If the target crosses a function boundary, run the **architect** skill (planned W4) for parallel design exploration of the shape before the move. Until it ships, compare two or three target shapes yourself and record `architect skipped: planned W4`.
4. Subtract before you add. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape (**principle-subtract-before-you-add**, planned W3). The smallest change that reaches the target shape ships (**principle-laziness-protocol**, planned W3). A speculative cleanup that "might help" gets reverted.
5. Move in small behavior-preserving steps, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave (**principle-migrate-callers-then-delete-legacy-apis**, planned W3). No compatibility shims, no parallel old-and-new paths. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. Delegate the mechanical edits to a `poteto` subagent per `references/delegation.md`, with `model: "task:coding"` and a specific scope: file paths, the names being moved, and the behavior to hold.
6. Prove behavior is unchanged on the real artifact, not "it compiles" (**principle-prove-it-works**, planned W3). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface with the project's own tooling.
7. Confirm the change is worth keeping. The success measure is reduced reader load (**principle-minimize-reader-load**, planned W3). If the diff does not lower reader load somewhere, revert it.
8. When commits are allowed, rebase into small ordered commits. A subtraction commit, then the reshape, then any follow-on cleanup. Shape them with **principle-sequence-verifiable-units** (planned W3), so each behavior-preserving slice stays green before the next. Run **Opening a PR** (`playbooks/opening-a-pr.md`) only when the task authorizes a pull request.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
